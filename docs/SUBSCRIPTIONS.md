## Proposed product

One subscription per business, with monthly and annual billing. Start with a straightforward business plan; staff-seat tiers can follow. Prices are approved as above; included staff and the trial policy still need final configuration. AI must have a separate server usage budget/allowance rather than an unlimited-cost promise. This is software access billing, separate from invoices that electricians issue to their customers.

Stripe-hosted Checkout and Customer Portal are the proposed payment interfaces. The portal can manage payment methods, subscription changes and invoice history. Each existing business gets a server-owned Stripe customer binding; an owner manages their own business's billing. Staff roles do not inherit payment-management powers.

## Implemented policy

`lib/billing/subscriptionAccess.mjs` is a pure server-policy foundation, currently unused by runtime code. A paid feature predicate requires exact business/environment/product matching, a known active subscription, an explicitly clear service-owned review marker and an unexpired paid-through instant; a bounded provider trial is separately recognised. Cancellation at period end retains coverage until that boundary; failed/unpaid/paused/canceled/unknown states do not unlock paid features. Test records cannot enable live access. Trial completion cannot masquerade as a paid invoice. Billing management requires verified active owner membership for the same business.

Inputs must come from trusted server records reconciled with Stripe, including a join of the business Customer review flag as `reviewRequired`. The subscription snapshot alone is insufficient; missing or nonboolean review provenance denies paid/trial features. This helper is not authentication, signature verification, RLS, payment proof or a complete billing integration. Normal tenant/role permissions always apply. Browser flags, redirects and cached records cannot be authorities. Existing access is not gated by this module yet.

## Integration sequence

1. **Choose product settings.** Business subscription basis, GBP prices, monthly/annual price IDs, included staff, trial and AI allowance. Keep test/live identifiers and secrets separate; never accept a client-provided price, customer ID or organisation binding as authority.
2. **Server-owned persistence.** Add billing customer/subscription tables and an event inbox with database uniqueness constraints. Clients cannot write billing status, paid-through coverage or provider IDs. Owner reads are tenant-scoped. Apply and verify migrations/RLS in isolated tests before any hosted migration.
3. **Authenticated owner Checkout and portal routes.** Verify current user, active business membership and owner role on the server. Resolve the bound customer and allowlisted price server-side; prevent concurrent duplicate subscriptions/sessions with durable idempotency. Use fixed approved return origins. No card details are stored in JR OS.
4. **Verified webhooks and reconciliation.** Use Stripe's supported SDK to verify signatures over the untouched raw request body. Store event IDs durably for retries. Delivery order is not authoritative: serialize/reconcile each subscription against current provider state, and handle duplicate/concurrent/old events. Paid-through coverage extends only from verified payment evidence. A success redirect never grants access.
5. **Billing screen.** Show actual server-reported plan, payment state, renewal/cancellation date and invoice/portal actions. Clearly distinguish test billing, pending setup, payment problems and inactive subscription; no simulated successful payment buttons.
6. **Enforcement.** Apply commercial entitlements to server APIs and direct database/RPC write paths; a frontend paywall alone is bypassable. Preserve authenticated read/export access to existing customer data when a subscription ends, without overriding revoked tenant membership. Provision existing JR access through an explicit server-managed migration policy, never a browser exemption.
7. **Acceptance before launch.** Test checkout, 3DS/payment failure, renewal, portal cancellation, duplicate sessions/events, out-of-order delivery, expired trial, organisation switches, test/live separation and read/export after expiry. Connect AI requests to tenant subscription and usage limits. Verify hosted test mode end-to-end before activating live charging.

## Payment review holds (implemented, inactive)

A supported verified refund, dispute, early fraud warning or credit note now resolves its current resource through the sandbox Stripe SDK. Charge-based signals use the current Charge Customer; credit notes check the current Invoice and matching Customer. The existing unique mode/account/Customer binding owns the business. Event metadata or a submitted Customer cannot select the business. These Customers are reserved for JR OS software billing; job-customer invoicing/Connect payments belong to separate boundaries.

The worker atomically marks a service-owned customer review flag, finishes the event in review and releases the matching current event/business leases. It writes no paid coverage. The first marker source/reason/event/time is retained and browser roles cannot read or alter it. Later paid/trial/cancellation reconciliation and void/zero signals cannot clear it. A positive current refund or issued positive credit note marks review; any verified dispute or fraud warning requires explicit review even if resolved/non-actionable. This conservative customer-wide policy can require an operator check for a legitimate refund or older resolved issue. It does not attempt subscription-specific loss allocation or identify a user as fraudulent.

The owner projection and HTTP/client expose only `reviewRequired:boolean`. A held business sees **Payment needs review**, rather than active/trial/payment-pending claims. Monthly/annual signup is unavailable, including server reservation and repeated signed-owner checks between provider operations and before URL return. Missing review provenance fails closed. Otherwise configured owner Portal access remains available to view invoices, update a payment method or cancel. Neither a browser flag nor Portal payment update clears the hold.

There is no operator clearance/release workflow yet. Unknown, malformed, unsupported or unbound evidence remains review work without inventing ownership; provider outages retry and budget exhaustion defers. Those cases, backlog monitoring, operator resolution and real hosted acceptance are launch requirements. The pure paid/trial predicate now requires an explicit clear review state, but runtime subscription/AI enforcement is still unused. All flags remain off and the existing migration remains unapplied; no hosted keys, charges, refunds, emails or tax settings were changed.

A current owner's explicit Checkout review response also immediately switches the phone view to review and starts a fresh status read. The review presentation suppresses pending claims and repeat signup during loading/failure; authorization denial still takes precedence and otherwise configured Portal management remains available. This local presentation never writes the database or grants access. It stays for that owner-screen instance because a clear Customer Boolean alone cannot resolve a separately uncertain Checkout operation; future manual clearance can require leaving/reopening billing.
