# JR OS Stripe integration plan

Prepared 1 November 2026 using the connected Stripe implementation planner for JR Electrical Services, https://www.jrelectricalservices.org. Sandbox connection confirmed; guide `iguide_61VgOX4WP4umJi96141RxGUITlJWL` accepted. This records recommended design choices, not merchant pricing approval or a deployed payment integration.

## Product boundaries

| Purpose | Initial approach | Ownership |
| --- | --- | --- |
| Sell JR OS access | Stripe Billing, hosted subscription Checkout, Customer Portal | JR Electrical sells its own software subscription |
| Invoice for JR Electrical jobs | Invoicing API, reviewed drafts, Hosted Invoice Page | JR Electrical invoices its own customers |
| Other businesses collect their job payments | Separate future Stripe Connect design | Each business must have its own merchant/payment boundary |

JR OS currently uses Next.js/React, Netlify and Supabase business accounts. Its phone-friendly web/PWA interface follows the web Checkout path; a native app distribution would need a separate store/payment review. No Connect accounts, transfers or application fees are part of this initial implementation.

## Recommended first release

- Flat subscription per business. One Product per purchasable tier; monthly and annual GBP Prices for variants of the same tier. Jake approved GBP 29/month and GBP 290/year on 1 November 2026, plus the founding monthly offer below. Included staff and AI allowance remain undecided; a 14-day trial is proposed but not yet wired into Checkout.
- Standard Stripe-hosted Checkout with flexible billing mode and dynamic payment methods. Omit `payment_method_types`. Use `integration_identifier` with a stable flow label and an eight-random-letter suffix per current API guidance. Do not enable Managed Payments by assumption.
- Pay at signup is a proposed default, not a published policy. Do not configure a trial until Jake chooses it. Stripe Billing generates subscription invoices; do not create a second job invoice for subscription charges.
- Owner-only Customer Portal for payment methods, invoices and cancellation at period end. Enable plan switching only between approved compatible Prices. Choose proration behavior explicitly before offering changes.
- Configure Smart Retries and recovery emails before launch; planning has not enabled emails or changed account settings.
- Keep AI costs bounded by server-enforced business usage limits. Usage charging is outside this first release; if added later, evaluate Stripe's current Metronome recommendation separately.

## Review against existing code

`lib/billing/subscriptionAccess.mjs` and its six tests already provide a useful fail-closed predicate: exact business/mode/allowlisted Price, bounded paid/trial coverage, active owner management, and remaining paid coverage after scheduled cancellation. It is unused by runtime code and receives trusted records; it cannot authenticate users, verify payments or enforce database access.

The server-only Stripe SDK/provider boundary is now implemented and locally tested (see below). The following are still missing and required before selling access: an authenticated Portal route, hosted application of the prepared billing schema/customer bindings, worker activation/scheduling, automated risk handling, purchase UI activation, founding eligibility, paid-feature enforcement, AI usage limits and hosted sandbox acceptance. No Stripe API key or webhook secret was made available to the JR OS server through the plugin connection. Plugin OAuth authorizes these tools; it does not install server credentials.

## Implementation order

1. **Configuration and credentials.** Use a dedicated development sandbox; separate CI sandbox and live configuration. Pin the current supported Node SDK/API after checking the actual API contracts (Stripe guidance at planning time: Node SDK 23, API `2026-09-30.endive`). Create a least-privilege sandbox restricted key for the server and configure the webhook endpoint's own signing secret. Keep both in secure server deployment settings, never chat, git, browser code, public environment variables, analytics or logs. Prepare validated server-only names: `STRIPE_RESTRICTED_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_ACCOUNT_ID`, `STRIPE_MODE`, `STRIPE_PRICE_MONTHLY`, `STRIPE_PRICE_ANNUAL`, `STRIPE_PORTAL_CONFIGURATION_ID`, `APP_ORIGIN`. These are proposed names, not configured values. A full-page redirect does not require exposing a secret or adding an embedded card form.
2. **Persistence and authorization.** Add service-owned business/customer bindings, subscription snapshots, event inbox, durable operation/idempotency records and risk-review records. Unique constraints must prevent cross-business customer reuse and concurrent duplicate signup. Authenticate using current Supabase user and active membership; only an owner may manage billing. RLS must deny browser writes to payment identifiers, coverage, event state and entitlements. Validate test/live account scope throughout. Do not trust submitted customer IDs, Price IDs, metadata or redirect flags.
3. **Checkout and portal.** Server resolves business, bound Customer and approved monthly/annual Price. Create/reuse a durable pending operation under a database lock; use its key with Stripe. Handle an already subscribed or pending business without creating another subscription. Return only a provider URL. Use fixed configured HTTPS return origins, origin/CSRF protection and allowlisted provider URLs. Success shows pending confirmation until verified server state is available.
4. **Required webhook worker.** Verify the untouched request body with the SDK and signing secret before persisting anything. Durably enqueue event ID with uniqueness and recoverable work state; acknowledge after durable receipt, not before. Serialize per subscription/customer, retrieve current Stripe objects, and reconcile rather than applying events by delivery order. Failed work remains retryable; add periodic reconciliation for missed deliveries. Resolve ownership through stored Customer/Subscription IDs and provider object relationships, not event metadata alone.
5. **Subscription and risk events.** Handle relevant `customer.subscription.*`, `invoice.paid`, `invoice.payment_failed`, `checkout.session.completed` and asynchronous Checkout outcomes. A checkout completion does not by itself prove payment; invoice settlement must match the owned subscription, approved recurring items, mode and period. Map refunds, disputes and fraud warnings through current version-specific invoice/payment relationships. Act on `charge.refunded`, `charge.dispute.created` and `radar.early_fraud_warning.created` using auditable risk-review handling; do not automatically revoke all access for every partial refund. Include credit-note reconciliation for job invoices. Subscribe only to events the integration processes. Handle `customer.updated` if caching customer personal/billing details.
6. **Job invoicing.** Begin with JR Electrical's own business only. Owner reviews the job, approved quote version, customer, line items, VAT, deposit already paid and balance. Snapshot totals server-side; associate invoice items explicitly with the intended invoice to avoid sweeping unrelated pending items. Use durable per-job/milestone idempotency. Create drafts with `auto_advance:false`; an explicit separate action approves finalization/sending. Never auto-charge a saved method without the customer's appropriate agreement. Hosted Invoice Page collects customer payment. Reconcile paid/failed/void/credit-note/refund outcomes back to the right job. Deposits and final balances must not double-bill the same work.
7. **UI and enforcement.** Add a phone-friendly Billing screen with large Subscribe/Manage billing/View invoices actions and actual server plan, status, renewal and cancellation dates. Clearly show sandbox/setup/pending/payment-problem states. Apply subscription and AI allowance checks to APIs, workers, RLS and RPC write paths. Preserve authenticated historical read/export after expiry while respecting revoked memberships. Existing JR use needs an explicit server migration policy before any gate is enabled.

## Implemented provider boundary

`lib/server/stripeBilling.mjs` now provides sandbox-only validated configuration, subscription Checkout creation, Customer Portal creation and raw-body webhook verification using pinned Stripe Node SDK 23.1.0 / API `2026-10-28.endive` (the installed SDK's current supported version). Example variable names are in `.env.example`, with secret values left blank.

The disabled-by-default `/api/billing/webhook` receipt route now imports this module. The disabled Checkout HTTP route now uses it through the durable coordinator; the Portal HTTP route remains unimplemented. It accepts only trusted server operation records; it does not authenticate a caller, create customer bindings, acquire locks, deduplicate events or grant access. Future routes must verify active owner membership and own the durable business/customer/operation records before using it. All provider errors become fixed safe messages. Remote account, customer mode and approved Price configuration are checked before Checkout. Returns use the configured HTTPS app origin; returned URLs must use the exact Stripe Checkout/portal hosts. Retries of one persisted operation reuse the same provider idempotency key, including if an erroneous caller changes its plan; provider idempotency is not a substitute for durable business locking and must not be relied on beyond Stripe's retention period.

Only the standard monthly/annual plans are currently accepted. Founding offer requests fail closed until the server can enforce durable eligibility and one offer per business. Trial policy is not applied yet. The webhook verifier checks raw bytes/signatures, event shape and test mode only; it must feed the durable inbox/reconciliation worker before any fulfillment. It does not make webhook processing complete.

Focused tests use the real Stripe SDK with a local HTTP fixture server, not real Stripe credentials or hosted payment requests. They exercise request serialization, approved prices, scope/mode mismatches, retries, redirects and signature failures. Deployed sandbox acceptance and remaining implementation steps are still required.

## Prepared persistence and webhook receipt stage

`supabase/migrations/20261101154212_subscription_billing_store.sql` is prepared locally and included in the recovery chain, but has NOT been applied to the hosted database. It adds sandbox-only service-owned customer bindings, subscription snapshots, durable operations and an event inbox. Composite foreign keys prevent a subscription/operation from using another business's customer. Unique indexes limit a business to one pending Checkout and one current subscription. Browser roles have no table privileges or RLS policies; Mutation/worker RPCs are security-invoker and executable only by the service role. The owner-status read added below is a separate authenticated, sanitized exception.

Receipt inserts once per account/mode/event ID without replacing the original event. Claiming uses `FOR UPDATE SKIP LOCKED`, a 60-second lease and a fresh UUID token. Expired work is reclaimable; old tokens cannot finish it. Ten failed or crashed attempts require review. These inbox leases do not yet fence changes to subscription coverage: the future reconciliation worker must commit coverage plus event completion atomically under the current lease and business lock. Marking an event processed alone does not prove payment.

`app/api/billing/webhook/route.ts` verifies the bounded raw body with the Stripe SDK before calling the service-only receipt RPC. Duplicate receipt is acknowledged; failed, empty, malformed or oversized persistence responses return a safe retryable 503. Forged/live/Connect deliveries never reach storage. Supported subscription, invoice, Checkout and risk/credit-note events can be queued; unrelated events are acknowledged as ignored. The route is OFF unless `JR_OS_BILLING_WEBHOOK_ENABLED=true` and all required server credentials/configuration are present. **Keep it disabled until hosted migration checks and worker/reconciliation setup are complete.** No event processing worker, subscription fulfillment or paid access gate is activated by this change.

Local tests execute the actual migration in pinned PGlite 0.5.14 (Postgres WASM), checking grants/RLS, composite bindings, pending-operation uniqueness, duplicate receipts, lease recovery, stale token rejection and review exhaustion. HTTP-handler tests use signed fixtures and a controlled persistence boundary. Actual simultaneous database sessions, the full existing migration chain, Supabase hosted Auth/PostgREST/advisors, Stripe event delivery and live credentials remain unverified here and are required before activation.

The Supabase CLI generated the migration scaffold before automatic approval review blocked its attempted PostHog telemetry. The CLI was not rerun; implementation and tests used the already-generated local file and local Postgres. Review and apply the migration through an approved deployment path, verify the exact deployment marker and service-only permissions, and run hosted security advisors/acceptance before enabling the endpoint. No hosted account or schema changes were made in this stage.

## Implemented, unactivated reconciliation stage

`lib/server/billingWorker.mjs` now provides a one-event worker, a service-only RPC adapter and a disabled configured entry point. It is not scheduled or exposed through a public route. `JR_OS_BILLING_RECONCILIATION_ENABLED` defaults to false; webhook receipt also remains off. No hosted schema or account settings were changed.

Lifecycle, invoice and subscription Checkout events resolve their target through current Stripe objects, not event status, redirect flags or metadata. After acquiring the bound business's database lease, the worker re-fetches the current subscription and payment evidence through the pinned SDK. `lib/server/billingReconciliation.mjs` accepts only the approved GBP monthly/annual Price with one subscription item and quantity one. An active paid snapshot needs a matching latest invoice, exact non-prorated recurring line/period, paid InvoicePayment backed by a successful PaymentIntent and captured, undisputed, unrefunded charge. Bounded provider trials are distinct from payment; canceled/failed/unpaid/paused states do not record paid coverage. SDK reader requests use no automatic retries and a five-second timeout to fit within the business lease; expiry always prevents writes.

The existing **unapplied** migration has been extended in place with business reconciliation tokens and service-only begin/complete RPCs. Only one event can hold a business lease at a time. Snapshot upsert and event completion commit in one transaction, after checking the current event and business tokens/expiry under row locks. A stale worker cannot overwrite a newer snapshot or finish a newer attempt. Generic event retry/review also releases its own business lease, including when the acquisition response was lost. Bound customer/organisation fields cannot be reassigned through the snapshot upsert.

Uncertain or unsupported settlement enters review without extending coverage. Supported first-release evidence is intentionally narrow: credit-balance/zero-value/manual-out-of-band invoices, credit notes, split payments, proration and multi-item configurations require review. Invoice totals must match the due amount, starting/ending customer balances and credit-note amounts must be zero, and pretax credits must contain only supported discounts. Existing bounded coverage is preserved when review is required. Refund, dispute, fraud-warning and credit-note events are routed to review; **automated risk resolution/holds and a review UI are still required before public billing**. This is not a claim that those events have been financially reconciled.

Actual multi-session database locking, full hosted migration recovery/security advisors, service-key scopes, provider delivery, worker trigger/backoff, periodic recovery/reconciliation, Checkout operation recovery and production entitlement enforcement remain outstanding. The inbox now enforces 30-second retry backoff and 60-second deferral for a busy business. Deferral preserves the failure budget; ten genuine failures/crashes require review and the worker reports that persisted outcome. A future scheduler must still invoke bounded work rather than loop indefinitely. Keep both activation flags off until those checks and workflows are ready. Pricing/tax/trial/staff/AI allowance launch configuration also remains required; no VAT collection was enabled.

## Durable Checkout start engine (not publicly activated)

`lib/server/billingCheckout.mjs` now reserves one pending/open/review attempt per business, binds a server-created Stripe Customer under the current reservation token, records the provider Session before returning its URL, and resumes known open Sessions. The existing unapplied migration adds service-only reserve/bind/record/release RPCs and expands operation states. Reservation and writes check the active owner profile and serialize by business using a transaction advisory lock. Browser roles cannot invoke these mutation RPCs.

The coordinator requires a trusted owner identity plus a fresh normal-owner/session revalidation callback before provider mutations and redirects. The disabled authenticated Checkout HTTP route described below now supplies this context through signed Supabase verification and the owner-status guard, validates same origin/intended business, and accepts only a monthly/annual plan selector. Public purchase UI remains inactive. A caller-supplied owner object or a callback returning true is not authentication. The core module deliberately cannot make browser records authoritative.

Customer creation and Checkout use the persisted operation ID for stable provider idempotency; no browser metadata supplies ownership. Requested Checkout expiry and client reference are fixed on the durable operation. Unknown creation outcomes older than 20 minutes require review rather than a fresh attempt. Provider subscription listing blocks another purchase while an active/trialing/incomplete/past-due/unpaid/paused subscription exists, including before the local snapshot catches up. Partial/ambiguous provider lists fail closed.

Only a provider-confirmed expired Session can be replaced automatically. Known completed Sessions remain recoverable rather than permanently entering review; a current, same-customer/test-account Subscription must be canceled or incomplete-expired before that operation can be retired for signup again. Completed Checkout is never paid-access proof. If the reconciled local subscription still shows current coverage/status, reconciliation must catch up before signup resumes. No operation is cleared merely because a client timer or browser flag says it expired.

Tests execute real local SQL for reservation fencing, customer binding, repeats, lost committed responses, expired recovery, revoked owners and completed-then-canceled signup. SDK contract tests use local HTTP fixtures to check customer idempotency, subscription guards and Session scope. Hosted locking/PostgREST, actual provider responses, the signed-owner HTTP bridge, founding-offer eligibility and end-to-end financial tests remain required. No hosted schema, credentials, charges, emails, flags or VAT settings were changed in this stage.

## Authenticated Checkout HTTP bridge (disabled by default)

`POST /api/billing/checkout` now connects the durable engine to the shared signed-owner verifier extracted from the existing billing-status handler. Only an exact `{plan: "monthly"}` or `{plan: "annual"}` body is accepted. The client cannot supply customer IDs, Price IDs, role/owner claims, return URLs or acceptance flags. Same-origin checks retain the approved Netlify immutable/alias mapping; missing tokens, wrong business and unsupported payloads fail before privileged work.

The verifier calls Supabase Auth and the owner-status RPC using the public key plus user bearer. It binds the actor and intended organisation, and repeats live normal-owner/session verification before provider mutations and URL return. Service credentials are used only for the durable operation RPCs, never for user verification. Revocation/recovery/actor changes, request cancellation and auth outages cannot grant access or return a Checkout link. Errors are fixed safe codes; busy/conflicting/review/subscribed states return 409, auth denial 401/403, invalid bodies 400 and setup/provider failures 503. Responses are uncached and rebuilt with only mode, Session ID and an exact HTTPS Stripe Checkout URL.

Execution requires all four server flags: `JR_OS_BILLING_CHECKOUT_ENABLED`, `JR_OS_BILLING_WEBHOOK_ENABLED`, `JR_OS_BILLING_RECONCILIATION_ENABLED` and `JR_OS_BILLING_SANDBOX_VERIFIED`, plus validated sandbox credentials/configuration. Every flag remains false in the example and no hosted flag was changed. The verified flag is an operator acceptance gate, not automatic proof of testing: complete real hosted sandbox checks before setting it. Billing status still reports `checkoutAvailable:false` and the phone's payment controls remain disabled.

API tests combine the real coordinator, service store, actual local SQL and the latest owner/session helper definitions with a controlled external Stripe boundary. They cover revocation after reservation and after Session recording, disconnects at both points followed by retry reuse, recovery, cross-business/staff access, strict input/origin checks and fixed errors. Actual browser disconnects/hosting timeouts, full hosted schema/role/PostgREST behavior and real Stripe acceptance remain unverified. No real provider call, credentials, hosted schema change, charges or VAT activation occurred here.
